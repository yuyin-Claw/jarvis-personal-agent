# JARVIS Product Requirements Document

> 版本 0.1 · 状态 Draft · 提取自《Omarchy改造目标》备忘录（2026-11-14）

JARVIS Personal Agent
Product Requirements Document（PRD）
版本： 0.1 状态： Draft 产品定位： System-level Personal Agent 基础平台： Omarchy / Arch Linux 目标形态： Persistent Digital Human + Central Agent
1. 产品概述
1.1 产品定义
JARVIS 是一个运行于个人计算环境中的系统级 Personal Agent。
它拥有统一的人格、长期记忆、环境感知、任务管理和自主执行能力。
用户通过自然语言与 JARVIS 持续交流。JARVIS 负责理解用户意图、理解当前环境、维护长期目标，并根据任务需要调用不同的 Harness 完成工作。
用户不需要直接管理模型、Agent、Skills、MCP 或执行工具。
JARVIS 是用户唯一的智能交互入口，其他执行系统均作为其能力来源。
1.2 产品核心理念
One Persona, One Conversation, Multiple Execution Engines.
一个稳定的人格。
一个持续存在的对话关系。
一个统一的中央决策系统。
多个可替换、可扩展的执行环境。
一个持续学习和扩展能力的个人智能体。
1.3 产品愿景
让操作系统从传统的应用程序运行环境，逐渐演变为以个人 Agent 为中心的计算环境。
传统模式：
用户 → 应用程序 → 工具 → 结果
JARVIS 模式：
用户目标 → JARVIS 理解 → 自主调度 → Harness 执行 → 结果验证 → 持续沟通
2. 产品设计原则
2.1 人格统一
JARVIS 始终以同一个人格与用户交流。
底层可以存在多个模型、Harness 和专业 Agent，但它们不能造成用户交互关系的碎片化。
JARVIS 负责最终决策和对话，不允许不同 Harness 各自成为用户的独立主控 Agent。
2.2 对话优先
默认界面只有 JARVIS 数字人及对话入口。
不主动展示复杂的 Agent 管理面板、任务管理后台或系统 Dashboard。
当用户要求查看数据、项目状态、研究成果或执行进度时，JARVIS 可以调用 Harness 动态生成相应界面。
2.3 持续存在
JARVIS 不依赖聊天窗口持续打开。
它应该作为后台服务持续运行，维护任务状态、接收系统事件、跟进长期目标，并在合适的时候主动联系用户。
2.4 主动而不过度打扰
JARVIS 可以：
主动发现任务风险。
关注项目进度。
识别用户可能遇到的问题。
提前开展准备性研究。
启动低风险的后台 Harness 任务。
主动提供建议和结果。
但必须尊重用户的专注状态、隐私模式和通知偏好。
2.5 自我扩展
JARVIS 不局限于预先开发的工具。
当发现能力缺口时，可以调用 Harness Factory，设计、开发、测试和注册新能力。
任何新能力都必须经过安全验证，权限提升必须由独立授权机制控制。
2.6 系统独立性
JARVIS Core 不应该与 Omarchy 内部脚本形成强耦合。
Omarchy 是首个运行平台，而不是 JARVIS 的全部产品边界。
3. 目标用户及使用场景
3.1 目标用户
第一阶段主要面向：
高频使用计算机的个人用户。
软件开发者和技术研究人员。
需要长期管理多个项目的知识工作者。
希望让 AI 持续参与个人工作流程的用户。
3.2 核心使用场景
场景 A：日常对话
用户可以随时通过语音或文字与 JARVIS 交流。
JARVIS 能够理解当前对话，并关联历史记忆和项目上下文。
场景 B：复杂任务委派
用户提出一个目标，JARVIS 自动选择 Harness，分解任务、执行和验证结果。
场景 C：长期任务跟进
用户委派长期目标后，JARVIS 在后台持续跟踪，并在重要节点主动沟通。
场景 D：环境感知
JARVIS 在获得授权后理解用户正在使用的应用、屏幕、文件、浏览器和语音环境。
场景 E：主动协助
JARVIS 根据环境变化和长期目标，发现值得关注的问题，主动准备解决方案。
场景 F：能力扩展
JARVIS 发现自身缺少某种工具或执行能力，通过 Harness Factory 创建新的 Harness、Skill 或 MCP。
场景 G：按需生成界面
用户要求查看项目进度、分析数据或管理系统时，JARVIS 动态生成交互界面。
4. 核心功能需求
FR-01：统一人格和对话系统
优先级：P0
要求：
一个统一的 JARVIS 身份。
支持文字交互。
支持语音交互。
支持连续对话。
支持历史对话检索。
支持多模型接入。
能够将 Harness 输出转换为统一的用户沟通内容。
人格要求：
理性、冷静、专业。
类似私人管家。
不过度拟人化。
能够主动提出建议。
了解用户长期目标。
能够承认不确定性和执行失败。
FR-02：中央 Agent Orchestrator
优先级：P0
负责：
理解用户意图。
识别任务类型。
制定任务计划。
选择 Harness。
管理任务生命周期。
监控执行状态。
处理失败和重试。
验证执行结果。
向用户汇报。
JARVIS Core 是唯一的中央决策入口。
FR-03：LLM Gateway
优先级：P0
支持：
OpenAI 兼容接口。
不同模型提供商。
本地模型。
模型切换。
根据任务选择模型。
模型调用日志和成本统计。
超时及故障处理。
模型与 Agent Runtime 解耦，不允许业务逻辑直接绑定某个厂商。
FR-04：Memory Engine
优先级：P0
记忆内容包括：
用户偏好。
用户长期目标。
项目资料。
历史决策。
对话摘要。
任务结果。
用户纠正的信息。
重要活动上下文。
要求：
支持长期存储。
支持语义检索。
支持关联检索。
支持来源追踪。
支持修改和删除。
支持记忆置信度。
支持用户控制自动记忆。
第一版采用 SQLite，后续可增加向量数据库及知识图谱。
FR-05：Task Manager
优先级：P0
任务状态：
CREATED
PLANNED
WAITING_APPROVAL
RUNNING
BLOCKED
COMPLETED
FAILED
CANCELLED
要求：
任务持久化。
支持长时间运行。
支持后台执行。
支持任务恢复。
支持任务取消。
支持任务依赖关系。
支持定时任务。
支持任务历史记录。
FR-06：Harness Runtime
优先级：P0
第一阶段接入：
Codex Harness。
Claude Code Harness。
统一接口要求：
能力声明。
任务提交。
执行状态查询。
流式进度。
日志获取。
结果获取。
文件产物管理。
取消任务。
超时处理。
Harness 必须以独立执行进程或隔离环境运行。
不得假设某个 Harness 一定提供可长期依赖的内部 API。
优先采用厂商正式支持的 CLI、SDK 或协议接口。
FR-07：Continuous Runtime
优先级：P0
要求：
后台常驻运行。
事件接收。
定时任务。
心跳检查。
任务状态监控。
断线恢复。
主动沟通触发。
用户离线后的任务状态保存。
不允许通过持续无休止地调用大模型实现心跳。
应该采用事件驱动、规则判断和按需模型调用。
FR-08：Proactive Engine
优先级：P0
负责判断：
是否需要主动联系用户。
是否需要跟进某项任务。
是否可以提前启动 Harness。
是否应该暂缓打扰。
是否需要用户决策。
支持：
项目进度提醒。
任务阻塞提醒。
研究结果通知。
长期目标跟进。
用户指定的定时检查。
必须具备频率限制、去重、静默时间和用户偏好设置。
FR-09：Context Awareness Engine
优先级：P1
环境感知范围采用 Ambient。
数据来源：
当前窗口。
应用状态。
工作区状态。
屏幕内容。
语音。
浏览器。
文件变化。
用户主动选取的内容。
系统事件。
要求：
实时事件接收。
事件去重。
时间线建立。
活动识别。
项目关联。
上下文构建。
置信度管理。
敏感内容过滤。
感知推断必须与事实记录分开。
FR-10：Permission & Privacy Broker
优先级：P0
要求：
感知权限和执行权限分离。
按来源授权。
按目录授权。
按应用授权。
按 Harness 授权。
按操作风险分级。
敏感内容过滤。
权限撤销。
审计日志。
屏幕、麦克风、摄像头和剪贴板不得因为安装 JARVIS 而默认开放。
FR-11：Harness Factory
优先级：P2
要求：
识别能力缺口。
设计新 Harness。
生成 Skills。
生成 MCP Server。
自动化构建。
沙箱测试。
安全检查。
版本管理。
能力注册。
回滚和禁用。
JARVIS 可以自主开发和测试能力，但不得自行授予新能力更高的权限。
FR-12：Avatar & Dynamic UI
优先级：P1
要求：
数字人常驻入口。
语音反馈。
文字对话。
状态反馈。
主动通知。
全局快捷键。
动态 UI Host。
按需生成交互界面。
第一版采用轻量 2D 数字人，不要求实时 3D。
5. 产品非目标（Non-Goals）
JARVIS 0.1 不做：
自研基础大模型。
替代 Codex 或 Claude Code 的编程 Harness。
完整替代 Omarchy 桌面环境。
默认全天候保存原始屏幕录制。
默认全天候保存原始麦克风录音。
无限制的 Shell 和系统权限。
一开始就实现多设备分布式 Agent。
一开始就实现复杂 3D 数字人。
预先开发大量固定 Dashboard。
6. 用户体验要求
6.1 默认交互
用户只需要找到 JARVIS。
可以通过：
全局快捷键。
语音唤醒。
桌面数字人。
通知入口。
开始交流。
6.2 任务执行体验
JARVIS 应该：
理解需求。
告知用户准备采取的行动。
选择执行环境。
在后台执行。
适时汇报进度。
完成后验证结果。
保存有价值的记忆。
6.3 主动沟通体验
JARVIS 的主动沟通应该具有：
相关性。
时机判断。
上下文连续性。
可解释性。
可关闭性。
不应把每个系统事件都变成通知。
6.4 动态界面
动态界面由 JARVIS 按需创建。
所有动态 UI 必须：
在受限环境中运行。
使用受控的数据接口。
不能绕过权限系统。
可以关闭。
可以保存用户认可的成果。
可以在需要时重新打开。
7. 非功能性需求
7.1 可用性
后台异常退出后能够恢复。
未完成任务状态持久化。
不因数字人窗口关闭而中断后台任务。
网络故障时保留任务状态。
7.2 性能
初期建议目标：
本地窗口事件处理延迟：P95 小于 500ms。
本地事件入库延迟：P95 小于 1s。
普通对话首字响应：在模型服务正常情况下尽可能控制在 2s 内。
无感知任务时保持低资源占用。
视觉和语音处理按需启用。
这些指标属于工程目标，需要通过原型测试验证。
7.3 安全
最小权限原则。
Harness 隔离执行。
凭证安全存储。
高风险操作审批。
敏感信息脱敏。
操作审计。
可撤销授权。
7.4 可扩展性
新模型通过 Gateway 接入。
新 Harness 通过 Adapter 接入。
新系统通过 Platform Adapter 接入。
新感知来源通过 Context Source 接入。
新能力通过 Skill / MCP / Harness Registry 注册。
7.5 可移植性
JARVIS Core 不直接依赖 Omarchy 私有脚本。
首期提供 Omarchy Adapter，后续可以增加其他 Linux 桌面适配器。

9. 产品成功指标
第一阶段不以 Harness 数量或模型数量作为成功标准。
核心指标：
用户能否通过一个入口完成不同类型的任务。
JARVIS 能否正确选择 Harness。
长任务能否在聊天窗口关闭后继续。
JARVIS 能否恢复中断的任务状态。
用户是否需要反复解释历史项目背景。
主动通知是否有实际价值。
是否存在误执行或越权操作。
用户是否愿意把长期任务交给 JARVIS。
10. 产品决策原则
当产品功能发生冲突时，按照以下顺序判断：
用户安全和隐私。
人格与对话连续性。
任务执行可靠性。
环境理解准确性。
主动性。
自我扩展能力。
UI 丰富程度。
最终产品定义：JARVIS 不是一个管理 Agent 的平台，而是一个拥有统一人格、持续认知和自主执行能力的 Personal Agent。
